# GitHub Copilot Instructions for Organic Bitcoin (obtc)

This file provides context and guidelines for GitHub Copilot when working with the Organic Bitcoin (obtc) codebase.

## Project Overview

This is **OBTCD**, a fork of the **btcd** (Bitcoin implementation in Go) that implements the Organic Bitcoin (obtc) protocol. This project is based on the btcd full node implementation and adds obtc-specific functionality including REAP (Resource Expiry and Allocation Protocol) and UTXO expiry mechanisms.

### Key Facts About This Project
- **Forked from**: btcd (Bitcoin full node implementation in Go by btcsuite)
- **NOT Bitcoin Core**: This is based on btcd, which is a separate Go implementation of Bitcoin
- **Goal**: Implement obtc protocol modifications on top of the stable btcd codebase
- **Target**: Create a mainnet-ready obtc blockchain with REAP consensus rules
- **Timeline**: 8-phase development plan to mainnet candidate

### Development Philosophy
- **Minimize changes**: All obtc modifications should be parameterized behind `IsOBTC()` conditions
- **Fork-friendly**: Keep upstream btcd compatibility where possible for easy updates
- **Consensus-critical**: REAP and expiry logic must be deterministic and thoroughly tested
- **Production-ready**: Target is a mainnet candidate, not an experimental implementation

### Primary Reference Documents
1. **`obtc_doc/obtc_roadmap_plan.md`** - The authoritative development roadmap and timeline
2. **obtc white papers** in `obtc_doc/` folder for protocol specifications
3. **btcd documentation** - Understand the base implementation we're building upon

**Critical**: All obtc protocol implementations must follow the roadmap timeline and be isolated behind obtc-specific conditional logic.

## Code Placement Guidelines

### Where to Put New OBTC Code

1. **Consensus-critical changes** (REAP validation):
   - `/blockchain/` - validation rules and chain state updates
   - All behind `IsOBTC()` conditional checks

2. **Network parameters**:
   - `/chaincfg/params_obtc.go` - new file for obtc-specific parameters
   - Modify existing params files only with obtc conditionals

3. **Mining modifications**:
   - `/mining/reap/` - new subdirectory for REAP logic
   - Integrate with existing `/mining/mining.go` template generation

4. **RPC extensions**:
   - Add obtc methods to existing `/rpcserver.go`
   - Follow existing btcd RPC patterns

5. **Indexing**:
   - `/blockchain/expiryindex/` - new package for expiry tracking
   - Follow patterns from `/blockchain/indexers/`

6. **Configuration**:
   - Extend existing `config.go` with obtc-specific flags
   - Add obtc network detection logic

### What NOT to Change

1. **Core btcd infrastructure**: Keep P2P, database interfaces, script engine unchanged
2. **Upstream compatibility**: Don't break existing btcd API unless absolutely necessary  
3. **Non-consensus code**: Avoid changes to logging, monitoring, etc.
4. **Build system**: Minimize Makefile/CI changes beyond obtc-specific needs

## Development Patterns

### Conditional Logic Pattern
```go
// Use IsOBTC() to isolate obtc-specific behavior
if chaincfg.IsOBTC(params) {
    // OBTC-specific logic
    return validateOBTCTransaction(tx)
} else {
    // Standard Bitcoin validation
    return validateTransaction(tx)
}
```

### File Organization Pattern
- Keep obtc code in separate files/packages where possible
- Use `_obtc.go` suffix for obtc-specific implementations  
- Import obtc packages only when `IsOBTC()` is true

### Testing Pattern
- All new code must have comprehensive tests
- Use table-driven tests for different scenarios
- Include both obtc and non-obtc test cases

## Integration Points

### Week-by-Week Integration
1. **Phase 1**: `/chaincfg/` - network parameters and genesis
2. **Phase 2**: `/blockchain/expiryindex/` - expiry tracking
3. **Phase 3**: `/mining/reap/` - REAP transaction construction  
4. **Phase 4**: `/blockchain/validate.go` - REAP validation rules
5. **Phase 5**: RPC extensions in `/rpcserver.go`
6. **Phase 6**: `/cmd/obtc-status/` - status server
7. **Phase 7-8**: Hardening and release preparation

### Critical Success Criteria
- **Phase 4 Go/No-Go**: End-to-end REAP must work or switch to simplified REAP
- **Phase 6 Go/No-Go**: New nodes must sync in <2 hours or limit external access
- **Phase 8 Go/No-Go**: 72-hour continuous operation required for mainnet candidate

## Common Pitfalls to Avoid

1. **Don't break upstream compatibility** - Always use conditional logic
2. **Don't modify consensus rules outside IsOBTC() paths** - Risk of Bitcoin chain fork
3. **Don't add unnecessary complexity** - Follow "minimize changes" philosophy
4. **Don't ignore the roadmap timeline** - Strict 8-phase schedule with go/no-go gates
5. **Don't create GUI or complex explorers** - Focus only on core protocol

## When Making Changes

1. **Read the roadmap first** - Understand the current week's goals
2. **Check IsOBTC() pattern** - Ensure proper conditional logic
3. **Follow existing btcd patterns** - Don't reinvent the wheel
4. **Add comprehensive tests** - Both unit and integration tests
5. **Consider upstream merge conflicts** - Minimize diff surface area

This is a production-focused fork with a specific timeline. Code quality, determinism, and maintainability are more important than clever optimizations.
