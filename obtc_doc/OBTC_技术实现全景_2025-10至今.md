## 1. 系统总览：OBTC 到底“实现”了什么

OBTC 当前形态不是 Genesis-from-zero 的新链，而是 **Bitcoin 历史连续 + 分叉后规则分阶段激活**。其系统工程价值在于：

- 继承已有历史与成熟验证模型；
- 在分叉后引入具有明确目标的差异化规则；
- 通过分阶段激活降低一次性硬切换风险。

### 1.1 三层架构（职责边界清晰）

1. **Consensus Layer（节点共识层）**
   - 负责判定“什么交易/区块是合法的”。
   - 核心规则：Expiry、REAP 约束、Replay Protection 激活后的签名域强制。

2. **Mining & Policy Layer（出块与策略层）**
   - 负责“在合法集合里怎么选交易、怎么组块”。
   - 核心策略：REAP 只在模板内构造，mempool 不接收 REAP，模板预留 REAP 权重空间。

3. **Wallet Execution Layer（钱包执行层）**
   - 负责“用户如何看见风险、如何主动规避到期损失”。
   - 核心能力：`obtc.getexpiry`、`obtc.renew`、`renewall`、Auto-Renew Scheduler。

### 1.2 设计目标不是“增加功能”，而是“控制风险”

OBTC 的三条主线本质都是风险控制：

- **资产时间风险**：用 Expiry + Renew + REAP 明确生命周期。
- **跨链重放风险**：用 Namespace Isolation + Replay-Protected Sighash 双层防护。
- **执行稳定性风险**：用阶段激活 + 硬化规则 + 调度退避，避免系统震荡。

### 1.3 阶段化激活是核心工程策略

OBTC 并非在 fork 高度一口气启用所有变化，而是：

1. 先 fork（链身份分离）
2. 再启用 Expiry 约束
3. 再启用 REAP 共识硬化（顺序与上限）
4. 最后强制 Replay Protection

这种分层启用使得每一阶段都可单独验证、回归和观测。

## 2. 关键参数全集（含解释）

参数不是文档注释，而是系统行为的“硬开关”。下面每个参数都对应明确后果。

## 2.1 三网分叉与阶段激活参数

| 网络 | Fork Height | Expiry Index Start | Expiry Enable | REAP Hardening | Replay Protection |
|---|---:|---:|---:|---:|---:|
| Mainnet | 950000 | 950000 | 1050000 | 1060000 | 1065000 |
| Testnet | 2800000 | 2800000 | 2800100 | 2800120 | 2800130 |
| Regtest | 100 | 100 | 110 | 112 | 114 |

### 参数含义透视

- **Fork Height**：链身份分歧点，之前与 Bitcoin 规则一致。
- **Expiry Enable**：到期花费约束正式生效点。
- **REAP Hardening**：REAP 输入顺序与输入数上限升级为共识约束点。
- **Replay Protection**：强制签名域隔离点（未满足语义将直接验证失败）。

## 2.2 Expiry 参数

| 网络 | WindowBlocks | ListBatchLimit | ReapMaxInputs |
|---|---:|---:|---:|
| Mainnet | 3,679,200 | 10,000 | 256 |
| Testnet | 1,008 | 5,000 | 500 |
| Regtest | 144 | 1,000 | 200 |

### 参数影响

- **WindowBlocks** 决定 UTXO 生命周期长度。
- **ListBatchLimit** 决定查询分页单页上限，影响 RPC 性能和内存压力。
- **ReapMaxInputs** 直接限制单个 REAP 交易复杂度与资源占用上界。

## 2.3 Namespace Isolation 参数（防混链、防误转）

OBTC 与 BTC 在以下字段上隔离：

- **Network Magic**：`0x4F425443` (Main), `0x4F544553` (Test), `0x4F524547` (Reg)
- **Default Port**：8555 / 28555 / 28666
- **Bech32 HRP**：`obtc` / `obtct` / `obtcrt`
- **Address Prefix / Witness Prefix**：独立字节域
- **HD Key Version**：独立扩展公私钥版本
- **BIP44 Coin Type**：20260 / 20261 / 20262

### 为什么这很关键

仅改链 ID 不足以防误操作。真实系统里，用户最常见事故是：

- 地址看起来“像对的”，但实际跨链；
- 钱包导入扩展公钥时命名空间冲突；
- 节点误连到错误网络。

OBTC 的做法是“多维隔离 + 启动期冲突强校验”，不是靠用户自觉。

## 2.4 REAP 默认策略参数（矿工侧）

- Sort Mode：`Strict`
- Max Inputs（Mainnet）：256
- Weight Budget（Mainnet）：200,000 weight
- Scan Batch：按网络
- Tax Ratio：30%
- Dust Threshold：546 sat

### 核心含义

- **Strict 排序**确保不同实现最终选择一致，减少分歧概率。
- **Weight Budget**确保 REAP 不会无限吞噬区块资源。
- **Dust Fold Rule**避免制造不可经济花费输出。

## 2.5 Auto-Renew 默认参数（钱包侧）

- Enabled：false
- Interval：30m
- Failure Backoff：15m（0 可关闭）
- Window：`window_end <= blocks_to_expiry <= window_start`
  - 默认 `window_start=52560`
  - 默认 `window_end=25920`
- MaxUtxosPerRun：100
- MaxFeeRate：5000 sat/KB
- MaxRenewAmountPerRun：0（unlimited）
- `autorenewamount`：启用时必须大于 0

### 参数意图

- 这是“守旧型默认值”：先控制风险，再逐步放量。
- Backoff 与 Budget 两个参数共同约束“失败风暴”和“过量续期”。

## 3. Expiry 机制：从公式到共识行为

## 3.1 基本模型

UTXO 创建高度记为 `h_create`，到期窗口记为 `W`，则：

`h_expiry = h_create + W`

当 `h_tip >= h_expiry`，该 UTXO 进入 expired 状态。

### 状态分类

- **ok**：距离到期仍远
- **expiring**：在预警阈值内
- **expired**：已到期

这个分类用于 Wallet UX 与自动续期策略，不直接改变链共识本身。

## 3.2 Expiry Index：双向索引结构

系统维护两条映射：

1. `OutPoint -> ExpiryKey`
2. `ExpiryKey -> OutPoint Set`

这样设计的原因：

- 花费时快速删除（通过 OutPoint 定位）
- 扫描时按到期键顺序枚举（通过 ExpiryKey range scan）

## 3.3 Connect / Disconnect 行为

- **ConnectBlock**：新增输出写入索引；已花费输入从索引移除。
- **DisconnectBlock**：反向操作，恢复回滚前状态。

这保证 Expiry Index 在 reorg 下仍可保持与主链状态一致。

## 3.4 分页扫描与游标续扫

支持 `(fromKey, toKey, maxResults, startAfter)` 语义：

- `fromKey/toKey`：高度范围
- `maxResults`：单页上限
- `startAfter`：在同一 expiry 键内继续向后扫描

结果中可携带“下一游标”，支持大规模迭代而不丢顺序。

## 3.5 共识约束（激活后）

当 Expiry 规则启用后：

1. 非 REAP 交易花费 expired UTXO => 拒绝
2. REAP 交易花费 non-expired UTXO => 拒绝

这两个约束把“到期资产处理路径”强制收敛到 REAP。

## 3.6 性能与复杂度直觉

- 索引写入随交易输出数线性增长。
- 查询扫描随结果页大小增长，非全表扫描。
- 通过 BatchLimit 避免单次 RPC 造成数据库长事务与大内存分配。

## 4. REAP 机制：系统回收交易如何被选、被造、被验

## 4.1 REAP 的功能定位

REAP 不是“用户交易模板”，而是系统在区块内执行的资产回收事务。目标是：

- 将 expired UTXO 从长期沉积状态中清理；
- 将价值分解为 Refund 与 Tax；
- 让矿工有激励处理积压过期资产。

## 4.2 Candidate Selection Pipeline

一个 REAP 轮次的逻辑链：

1. 从 Expiry Index 扫描到期候选（`expiry <= tip`）
2. 用 UTXO 视图过滤无效或已花费输入
3. 对候选做 Deterministic 排序
4. 在 `MaxInputs` 与 `WeightBudget` 双约束下截断
5. 计算税与返还，形成 REAP Plan

## 4.3 Deterministic 排序规则

在 Strict 模式下，排序键顺序是：

1. ExpiryKey（先到期优先）
2. Amount（小额优先）
3. OutPoint（Hash + Index）

为什么要 deterministic：

- 不同节点构造 REAP 时应收敛到同序列，减少“实现差异导致模板差异”。

## 4.4 Weight 预算是保守上界，不是事后补救

REAP 使用保守估算公式限制构造规模，防止交易构造后才发现超重：

`EstWeight = Base + N*InputUpper + N*RefundUpper + Marker`

这类上界估算可提前截断候选，降低反复试构造的浪费。

## 4.5 Tax / Refund / Dust 处理

每个输入金额 `v`：

- `tax = floor(v * 30 / 100)`
- `refund = v - tax`

若 `0 < refund < dust_threshold`，执行 Dust Fold：

- `refund -> 0`
- `tax += refund`

意义：避免生成“看似返还、实则不可花费”的垃圾输出。

## 4.6 Blueprint 交易结构

REAP 交易结构特征：

- `version = 3`
- 输入为 expired outpoints
- 输出为：
  1. 按 script 聚合后的 refund 输出（减少输出膨胀）
  2. `OP_RETURN` marker 输出（value=0）
- marker payload：`REAP:<height>:<count>:<digest>`

并维护金额不变量：

`sum(inputs) = sum(refunds) + sum(tax)`

## 4.7 Marker Digest 的作用

Digest 对“有序输入列表”做摘要，用来把以下事实绑定在一起：

- 此 REAP 处理的是哪些输入；
- 输入顺序是否被篡改；
- 标记中的 count 与实际输入数是否匹配。

这是防“改 marker 不改输入”或“改输入不改 marker”攻击的重要锚点。

## 5. REAP 共识硬化：为什么必须上升到共识层

在硬化高度之后，REAP 不再只是“推荐实践”，而是“必须满足”。

## 5.1 Canonical Input Order 强制

规则要求 REAP 输入严格按 canonical order 排列。任何逆序都直接拒绝。

### 价值

- 消除排序歧义引发的实现分叉；
- 保证 marker digest 的语义稳定；
- 提升审计与重放分析可读性。

## 5.2 Max Inputs 上限强制

单个 REAP 交易输入数超过网络上限直接拒绝。

### 价值

- 限制单交易验证资源占用；
- 降低 DoS 面；
- 保持区块模板可预测性。

## 5.3 硬化后失败模式（应被预期）

- 输入顺序错 -> reject
- 输入超限 -> reject
- marker 高度/数量/digest 不一致 -> reject
- REAP 花费未到期输入 -> reject

关键结论：这些失败是“可证明、可预期、可复现”的，不是模糊行为。

## 6. Mining 与 Mempool 协同：系统交易如何“可落块”

## 6.1 Mempool 为什么拒绝 REAP

REAP 被定义为 block-internal system transaction。mempool 拒收可避免：

- 用户伪造系统交易扰乱 relay；
- 节点资源被无效系统交易占据。

## 6.2 Template 组块策略

策略是“两阶段”：

1. 先预评估 REAP 是否可构建；
2. 若可构建，则在常规交易选择时预留 REAP weight；
3. 常规交易入块后再追加 REAP，并再次做输入检查。

### 关键点

- 预留只在“REAP 可构建”时生效，不盲目扣空间。
- 若 REAP 最终追加失败，不影响常规交易模板成立。

## 6.3 Fee Accounting

REAP 的税额会计入区块总 fees，从而反映到 coinbase 收益。

这确保矿工有明确经济激励去处理到期资产，而非永远忽视。

## 6.4 与 SegWit / Taproot 校验的关系

常规交易仍走标准 script 验证路径；REAP 走专门的共识规则路径。两者边界清晰，不互相污染。

## 7. Replay Protection：从“命名隔离”到“签名域隔离”

## 7.1 威胁模型

仅做链参数隔离仍存在风险：

- 用户跨链复用私钥与脚本；
- 攻击者尝试在另一链复用签名语义进行 replay。

因此需要签名消息层的 domain separation。

## 7.2 两层防线

1. **Namespace Isolation**（地址/端口/HD version/coin type）
2. **Replay-Protected Sighash Domain**（签名消息域）

两层叠加可显著降低“配置失误 + 语义可重放”的联合风险。

## 7.3 Replay-Protected Sighash 机制

- 新增 `SigHash` 标志位（`0x40`）
- 对不同签名路径引入专用 tagged domain：
  - `OBTC/SigHashV0/v1`
  - `OBTC/SigHashV1/v1`
  - `OBTC/TapSighash/v1`

效果：即使交易结构近似，签名消息域不同，也不能跨链直接复用。

## 7.4 高度门控（Activation Gating）

规则并非“永远强制”，而是按网络高度切换：

- 激活前：保留兼容路径
- 激活后：必须满足 replay-protected 语义

这解决了一次性切换导致历史交易/工具链崩溃的问题。

## 7.5 三类签名路径差异化约束

1. **Legacy 路径**：哈希生成时加入 OBTC domain tag。
2. **SegWit v0 路径**：同样通过 domain tag 分离。
3. **Taproot 路径**：
   - 需要显式允许 replay-protected sighash type；
   - 激活后会校验 sighash type 是否包含 replay bit；
   - Key spend / Script spend 都受约束。

## 7.6 安全收益与工程代价

- 安全收益：跨链重放门槛大幅提高。
- 工程代价：签名工具链必须认知新 sighash 语义。

这是一种“以工具升级成本换取系统级资产安全”的选择。

## 8. Wallet 能力闭环：从可见风险到可执行动作

## 8.1 `obtc.getexpiry`：风险可视化

该接口把链上高度语义转换为用户可理解字段：

- outpoint
- amount
- create/expiry height
- blocks_to_expiry
- days_to_expiry
- status（ok/expiring/expired）
- dust_risk

### 核心价值

- 用户知道“哪笔资产在变危险”；
- 自动策略有稳定输入源；
- 审计与对账可复现。

## 8.2 `obtc.renew`：最小闭环的主动防护

核心输入：

- outpoints（显式指定）
- renew amount
- 可选 `target address / max fee rate / minconf`

核心输出：

- txid
- input/output count
- fee rate
- target address

### 设计上关键的一点

续期允许在账户范围内跨 key scope 选择指定输入，减少“看得见 UTXO 却续不了”的误伤。

## 8.3 `renewall`：批量化与定时化

支持：

- 按 status 过滤
- 按 `window_start/window_end` 过滤
- dry-run
- interval + runs 调度

这是把“人工逐笔续期”升级为“可运营流程”的关键步骤。

## 8.4 Auto-Renew Scheduler：进程内后台执行

执行循环的 gating：

1. policy enabled
2. wallet chain-synced
3. wallet unlocked
4. backoff 到期

候选构建逻辑：

- 读取 unspent outputs
- 计算 expiry info
- 窗口过滤
- `amount > renew amount` 过滤
- 按 `blocks_to_expiry` 升序
- `max_utxos` 截断
- `max_renew_amount_per_run` 再截断

## 8.5 两项硬化：Failure Backoff + Per-Run Budget

### Failure Backoff

- 单轮只要存在失败，下一次允许执行时间顺延 `failure_backoff`。
- 防止“持续失败 + 高频重试”造成日志风暴与资源浪费。

### Per-Run Budget

- 可把单轮总续期额限制在阈值内。
- 限制函数本质是：

`max_candidates_by_budget = floor(max_renew_amount_per_run / renew_amount)`

- 这可显式抑制“某一轮意外放量”。

## 8.6 Wallet 层风险边界

Wallet 能做的是“预警 + 续期执行 + 调度控制”，不能替代共识层。最终合法性仍由节点验证裁决。

## 9. 全场景与极端场景：预期行为矩阵

## 9.1 正常路径场景

1. 查询到 `expiring` -> 手动 `renew` 成功 -> 风险降低
2. `renewall` 在窗口内批量续期成功
3. auto-renew 定时执行，按优先级处理更近到期资产

预期：系统行为稳定、可预测、可复现。

## 9.2 边界场景

- 激活边界（`height = activation - 1 / activation / +1`）
- `window_start == window_end`
- `max_renew_amount_per_run` 精确整除/不整除 `renew_amount`
- REAP 输入数 = 上限
- REAP 权重估算命中边界

预期：边界行为无歧义，不出现“有时通过有时失败”。

## 9.3 极端运营场景

- 高 reorg 波动
- chain client 暂时滞后
- mempool 挤压到接近 block weight 上限
- 大量 dust-like UTXO

预期：

- 共识正确性优先于吞吐；
- 调度器在失败时降速而非失控；
- 模板策略在保留 REAP 与保证常规交易间平衡。

## 9.4 攻击与滥用场景

1. 伪造 REAP marker
2. 重排 REAP 输入
3. 构造超大输入集消耗验证资源
4. 跨链 replay 尝试
5. 向 mempool 注入伪系统交易

预期：

- 分别被 marker 校验、canonical order、max inputs、replay-protected sighash、mempool policy 拦截。

## 10. 运行期可观测性与运维建议

为让系统从“能跑”走向“可运营”，建议至少维护以下指标：

### 11.1 Consensus 侧

- expired spend rejection count
- REAP non-expired spend rejection count
- replay-protection violation count

### 11.2 Mining 侧

- template build attempts with REAP
- REAP append success rate
- reserved weight utilization
- REAP tax contributed to coinbase

### 11.3 Wallet 侧

- auto-renew candidate count / run
- auto-renew success/failure ratio
- backoff activated count
- per-run budget truncation count

### 11.4 风险告警建议

- 连续 N 轮 auto-renew failure
- REAP append success 连续低于阈值
- expiring UTXO backlog 持续上升

## 11. 白皮书重写建议：从“叙述文”升级到“状态机文”

建议新白皮书至少包含三个状态机：

1. **Activation State Machine**
   - Fork -> Expiry Enable -> REAP Hardening -> Replay Protection
2. **UTXO Lifecycle State Machine**
   - Alive -> Expiring -> Expired -> REAP Processed / Renewed
3. **Wallet Execution State Machine**
   - Detect -> Select -> Budget Gate -> Execute -> Backoff/Success

并增加四张强制表格：

- 参数常量表
- 激活高度表
- 错误码/失败类型表
- 责任边界表（Protocol / Miner / Wallet / User）

这样白皮书将从“理念说明”升级为“可审计规范”。

## 13. 结论

OBTC 当前实现已经从“概念提案”进入“可执行协议系统”阶段，其核心价值在于：

1. **规则可执行**：Expiry、REAP、Replay Protection 均有明确激活与失败语义。  
2. **跨层闭环**：Consensus、Mining、Wallet 三层逻辑已形成端到端路径。  
3. **风险可治理**：通过参数化、硬化规则、调度退避与预算上限，把系统风险收敛到可控区间。  

后续工作的重心不在于继续堆叠机制，而在于把已有机制做得更可运营、可观测、可解释：

- 持续强化运行期观测能力；
- 持续降低大规模场景中的波动与不确定性；
- 持续提升面向用户与外部生态的解释一致性。
