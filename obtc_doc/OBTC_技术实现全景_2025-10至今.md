## 1. 全局模型：OBTC 到底实现了什么

## 1.1 链形态与演进方式

OBTC 不是 Genesis-from-zero 新链，而是：

- 继承 Bitcoin 历史；
- 在 Fork Height 后进入独立规则域；
- 通过“分批激活”引入新规则（不是单点硬切换）。

这种模式的工程价值在于：

- 历史连续性强；
- 升级风险可分解；
- 每次规则变更可以独立验证与观测。

## 1.2 三层架构与职责边界

1. **Consensus Layer（节点共识层）**
   - 决定交易/区块是否合法。
   - 核心规则：Expiry、REAP 约束、Replay Protection 激活后签名域强制。

2. **Mining & Policy Layer（出块与策略层）**
   - 决定在合法交易集合内如何组块。
   - 核心策略：REAP 只在模板内构造；mempool 拒收 REAP；模板按条件预留 REAP weight。

3. **Wallet Execution Layer（钱包执行层）**
   - 决定用户如何发现风险、如何执行防护。
   - 核心能力：`obtc.getexpiry`、`obtc.renew`、`renewall`、Auto-Renew Scheduler。

## 1.3 三条主线（风险导向）

OBTC 当前实现不是“功能叠加”，而是三类风险治理：

- **时间风险**：Expiry + Renew + REAP（资产生命周期明确化）
- **跨链重放风险**：Namespace Isolation + Replay-Protected Sighash（双层隔离）
- **执行稳定性风险**：分批激活 + 硬化约束 + 调度退避（控制系统震荡）

## 1.4 激活顺序（高层状态机）

在 OBTC 规则域内，系统按以下顺序进入稳定形态：

1. Fork（链身份分离）
2. Expiry Enable（到期规则生效）
3. REAP Hardening（输入顺序与上限强制）
4. Replay Protection（签名域隔离强制）

## 2. 常量、参数与激活时序（System Constants）

参数是行为开关，不是注释。这里列出的每个值都直接影响系统行为。

## 2.1 三网激活矩阵

| 网络 | Fork Height | Expiry Index Start | Expiry Enable | REAP Hardening | Replay Protection |
|---|---:|---:|---:|---:|---:|
| Mainnet | 950000 | 950000 | 1050000 | 1060000 | 1065000 |
| Testnet | 2800000 | 2800000 | 2800100 | 2800120 | 2800130 |
| Regtest | 100 | 100 | 110 | 112 | 114 |

参数语义：

- **Fork Height**：规则分歧点；此前与 Bitcoin 保持一致。
- **Expiry Enable**：普通交易与 REAP 的到期花费约束开始生效。
- **REAP Hardening**：REAP 输入顺序与输入数上限进入共识强制。
- **Replay Protection**：签名域隔离进入强制校验。

## 2.2 Expiry 相关参数

| 网络 | WindowBlocks | ListBatchLimit | ReapMaxInputs |
|---|---:|---:|---:|
| Mainnet | 368,880 | 10,000 | 256 |
| Testnet | 1,008 | 5,000 | 500 |
| Regtest | 144 | 1,000 | 200 |

参数影响：

- **WindowBlocks**：决定 UTXO 生命周期长度。
- **ListBatchLimit**：决定 RPC 分页单页上限，影响内存与响应时延。
- **ReapMaxInputs**：共识级复杂度上限，限制单 REAP Tx 资源占用。

## 2.3 Namespace Isolation 常量

OBTC 与 BTC 在关键命名空间上做了硬隔离：

- **Network Magic**：
  - Main: `0x4F425443`
  - Test: `0x4F544553`
  - Reg: `0x4F524547`
- **Default Port**：8555 / 28555 / 28666
- **Bech32 HRP**：`obtc` / `obtct` / `obtcrt`
- **Address Prefix / Witness Prefix**：独立字节域
- **HD Key Version**：独立扩展公私钥版本
- **BIP44 Coin Type**：20260 / 20261 / 20262

关键点：系统启动时会做冲突校验，发现命名空间碰撞即失败退出。

## 2.4 REAP 默认策略常量（Mining 侧）

- Sort Mode：`Strict`
- Max Inputs（Mainnet）：256
- Weight Budget（Mainnet）：200,000 weight
- Scan Batch：按网络
- Tax Ratio：30%
- Dust Threshold：546 sat

这些常量的组合目标是：可预测、可收敛、可控资源占用。

## 2.5 Auto-Renew 默认常量（Wallet 侧）

- Enabled：false
- Interval：30m
- Failure Backoff：15m（0 可关闭）
- Window：`window_end <= blocks_to_expiry <= window_start`
  - 默认 `window_start=52560`
  - 默认 `window_end=25920`
- MaxUtxosPerRun：100
- MaxFeeRate：5000 sat/KB
- MaxRenewAmountPerRun：0（unlimited）
- `autorenewamount`：启用时必须大于 0

参数意图：默认保守，先控风险，再放吞吐。

## 3. Consensus Rulebook（协议硬规则）

本节只描述“必须成立”的规则。违反即 reject。

## 3.1 Expiry 计算与状态模型

定义：

- `h_create`：UTXO 创建高度
- `W`：WindowBlocks
- `h_expiry = h_create + W`

判定：

- `h_tip >= h_expiry` => expired

Wallet 侧会将状态细分为：`ok / expiring / expired`，用于 UX 与调度，但不改变共识判定。

## 3.2 Expiry Index 双向结构

索引保持两条映射：

1. `OutPoint -> ExpiryKey`
2. `ExpiryKey -> OutPoint Set`

原因：

- 删除快（由 OutPoint 反查）
- 扫描快（按 ExpiryKey 区间枚举）

## 3.3 Connect/Disconnect 与 Reorg 一致性

- ConnectBlock：新输出入索引，已花费输入出索引。
- DisconnectBlock：逆操作回滚。

因此在 reorg 下，索引状态可与主链状态保持一致。

## 3.4 分页与游标语义

扫描接口支持：`(fromKey, toKey, maxResults, startAfter)`

- `fromKey/toKey`：扫描区间
- `maxResults`：单页数量
- `startAfter`：同键内续扫位置

返回可携带下一游标，支持大规模连续读取，不需要全量拉取。

## 3.5 Expiry 生效后的共识约束

当 Expiry Enable 生效后：

1. 非 REAP 交易花费 expired UTXO => reject
2. REAP 交易花费 non-expired UTXO => reject

这把“过期资产处理路径”强制收敛到 REAP。

## 3.6 REAP 识别与标记绑定

REAP 交易由结构特征与 marker 共同识别，核心 marker 形态：

`REAP:<height>:<count>:<digest>`

共识会校验：

- marker 高度与区块上下文一致
- marker count 与输入数一致
- marker digest 与输入序列摘要一致

## 3.7 REAP Hardening（强制顺序 + 强制上限）

在 REAP Hardening 生效后，新增硬约束：

1. 输入顺序必须是 canonical order
   - `ExpiryKey` -> `Amount` -> `OutPoint`
2. 输入数不得超过网络上限（ReapMaxInputs）

## 3.8 典型 reject 模式（必须可预期）

- 非 REAP 花费 expired UTXO
- REAP 花费 non-expired UTXO
- REAP 输入顺序错误
- REAP 输入数超限
- marker 高度/数量/digest 不一致

关键结论：以上拒绝路径是规则性失败，不依赖实现“运气”。

## 3.9 Replay Protection 规则（共识门控）

威胁模型：仅做 namespace 隔离不足以完全消除跨链 replay 风险。

双层防线：

1. **Namespace Isolation**（地址/端口/HD version/coin type）
2. **Replay-Protected Sighash Domain**（签名消息域隔离）

Replay-Protected Sighash 机制：

- 新增 `SigHash` 标志位：`0x40`
- 专用 domain tag：
  - `OBTC/SigHashV0/v1`
  - `OBTC/SigHashV1/v1`
  - `OBTC/TapSighash/v1`

激活门控（Activation Gating）：

- 激活前：兼容旧语义
- 激活后：必须满足 replay-protected 语义

三类签名路径约束：

1. **Legacy**：hash 计算加入 OBTC domain tag
2. **SegWit v0**：hash 计算加入 OBTC domain tag
3. **Taproot（Key Spend / Script Spend）**：
   - 需要显式允许 replay-protected sighash type
   - 激活后检查 sighash type 是否包含 replay bit

收益与代价：

- 收益：跨链重放门槛显著提高
- 代价：签名工具链需理解并支持新语义

## 4. Mining & Policy Rulebook（组块与策略规则）

本节描述“在合法集合内如何组块”，属于 policy 与执行协同。

## 4.1 为什么 REAP 不进入 mempool

REAP 被定义为 block-internal system transaction，mempool 直接拒收。

目的：

- 阻断伪系统交易 relay 污染
- 避免节点资源被无效系统交易消耗

## 4.2 REAP 选择与构造流水线

单轮 REAP 的核心流程：

1. 扫描 `expiry <= tip` 候选
2. 用 UTXO 视图过滤失效输入
3. Deterministic 排序
4. 在 `MaxInputs + WeightBudget` 双约束下截断
5. 计算 Tax/Refund，形成 plan
6. 构造 blueprint 交易

## 4.3 Deterministic 排序规则

Strict 模式排序键：

1. ExpiryKey
2. Amount
3. OutPoint（Hash + Index）

目的：不同实现收敛到同一候选序列，降低模板分歧概率。

## 4.4 Weight 预算的保守上界控制

REAP 构造前先做保守估算：

`EstWeight = Base + N*InputUpper + N*RefundUpper + Marker`

这是前置约束，不是构造后补救。可减少反复试错。

## 4.5 Tax / Refund / Dust 规则

对输入金额 `v`：

- `tax = floor(v * 30 / 100)`
- `refund = v - tax`

若 `0 < refund < dust_threshold`：

- `refund -> 0`
- `tax += refund`

作用：避免产生经济上不可花费的微尘输出。

## 4.6 Blueprint 交易不变量

REAP blueprint 特征：

- `version = 3`
- 输入：expired outpoints
- 输出：script 聚合后的 refund 输出 + 1 个 marker 输出（`OP_RETURN`, value=0）

marker payload：`REAP:<height>:<count>:<digest>`

金额不变量：

`sum(inputs) = sum(refunds) + sum(tax)`

## 4.7 模板组块两阶段策略

策略是“先判断可建，再决定预留”：

1. 预评估 REAP 是否可构建
2. 仅当可构建时，对常规交易选择预留 REAP weight
3. 常规交易入块后尝试追加 REAP，并再次校验输入可行性

关键行为：

- 不盲目预留
- REAP 追加失败不破坏常规模板可用性

## 4.8 Fee Accounting

REAP 的 tax 会计入 block total fees，影响 coinbase 收益。

这使矿工处理 expired UTXO 具备明确激励，不是“纯义务动作”。

## 4.9 与 script 验证路径的边界

- 常规交易：走标准 script 验证路径
- REAP：走专门共识校验路径

边界清晰，降低规则交叉污染。

## 5. Wallet Rulebook（用户侧执行规则）

Wallet 的职责是“发现风险 + 执行动作 + 控制节奏”，不是替代共识裁决。

## 5.1 `obtc.getexpiry`：风险可见化

返回字段覆盖：

- outpoint
- amount
- create/expiry height
- blocks_to_expiry
- days_to_expiry
- status（ok / expiring / expired）
- dust_risk

价值：

- 人可读（用户可决策）
- 机可读（自动策略可消费）
- 可复现（审计与对账可追踪）

## 5.2 `obtc.renew`：最小闭环防护动作

输入：

- 显式 outpoints
- renew amount
- 可选：target address / max fee rate / minconf

输出：

- txid
- input/output count
- fee rate
- target address

关键实现意图：

- 在 account 约束下允许跨 key scope 处理指定输入，降低“可见但不可续期”的误伤。

## 5.3 `renewall`：批量化与定时化

支持：

- status 过滤
- `window_start/window_end` 过滤
- dry-run
- `interval + runs` 调度

意义：把人工逐笔操作升级为可运营流程。

## 5.4 Auto-Renew Scheduler：后台周期执行

执行 gating 条件：

1. policy enabled
2. wallet chain-synced
3. wallet unlocked
4. backoff 到期

候选构建步骤：

- 拉取 unspent outputs
- 计算 expiry info
- 应用窗口过滤
- 应用 `amount > renew amount` 过滤
- 按 `blocks_to_expiry` 升序
- `max_utxos` 截断
- `max_renew_amount_per_run` 再截断

## 5.5 两个硬化点（防失控）

### Failure Backoff

- 本轮只要有失败，下一轮允许时间顺延 `failure_backoff`
- 防止持续失败时高频重试造成资源风暴

### Per-Run Budget

- 限制单轮总续期金额
- 截断逻辑：

`max_candidates_by_budget = floor(max_renew_amount_per_run / renew_amount)`

- 用于抑制单轮异常放量

## 5.6 Wallet 边界声明

Wallet 负责预警与执行，不负责最终合法性定义。最终是否有效仍由节点共识验证裁决。

## 6. 端到端行为矩阵（Normal / Boundary / Extreme / Adversarial）

## 6.1 Normal 路径

1. `expiring` 被检测 -> 手动 `renew` 成功 -> 风险下降
2. `renewall` 在窗口内批量续期成功
3. auto-renew 周期执行，优先处理更近到期输入

预期：行为稳定、可预测、可复现。

## 6.2 Boundary 路径

- `height = activation-1 / activation / activation+1`
- `window_start == window_end`
- `max_renew_amount_per_run` 对 `renew_amount` 可整除/不可整除
- REAP 输入数命中上限
- REAP 估算 weight 命中边界

预期：边界行为无歧义，不出现随机通过/失败。

## 6.3 Extreme 运营路径

- 高频 reorg
- chain client 暂时滞后
- mempool 逼近 block weight 上限
- 大量 dust-like UTXO

预期：

- 正确性优先于吞吐
- 调度在失败时降速而非失控
- 模板在 REAP 与常规交易之间保持可控平衡

## 6.4 Adversarial 路径

- 伪造 marker
- 重排 REAP 输入
- 构造超大输入集
- 跨链 replay 尝试
- 向 mempool 注入伪系统交易

预期拦截点：

- marker 校验
- canonical order
- max inputs
- replay-protected sighash
- mempool policy

## 7. 可观测性与运维落地（Operate）

目标：从“能跑”升级到“可运营、可诊断、可告警”。

## 7.1 指标体系建议

### Consensus 侧

- expired spend rejection count
- REAP non-expired spend rejection count
- replay-protection violation count

### Mining 侧

- template build attempts with REAP
- REAP append success rate
- reserved weight utilization
- REAP tax contributed to coinbase

### Wallet 侧

- auto-renew candidate count / run
- auto-renew success/failure ratio
- backoff activated count
- per-run budget truncation count

## 7.2 告警建议

- 连续 N 轮 auto-renew failure
- REAP append success 连续低于阈值
- expiring UTXO backlog 持续上升

## 9. 术语对照表（Glossary）

| Term | 中文解释 | 在 OBTC 中的作用 |
|---|---|---|
| UTXO | 未花费交易输出 | 资产最小记账单元 |
| OutPoint | `txid:vout` 指针 | 唯一定位某个 UTXO |
| Expiry | 到期机制 | 给 UTXO 引入时间生命周期 |
| Expiry Height | 到期高度 | 决定何时进入 expired 状态 |
| WindowBlocks | 到期窗口块数 | 决定 UTXO 存续时长 |
| Expiry Index | 到期索引 | 支持快速扫描和删除 |
| Fork Height | 分叉高度 | 规则分歧起点 |
| Activation | 激活 | 新规则由“可配置”变“强制” |
| Consensus | 共识规则 | 决定区块/交易是否合法 |
| Policy | 策略规则 | 在合法集合内的本地选择逻辑 |
| REAP | 过期资产回收机制 | 处理 expired UTXO 的系统路径 |
| REAP Tx | 回收交易 | 区块内系统交易，不经 mempool relay |
| Marker | REAP 标记输出 | 绑定高度、输入数、摘要 |
| Digest | 摘要 | 防篡改、防重排 |
| Canonical Order | 规范顺序 | 降低实现差异与分歧风险 |
| Max Inputs | 输入上限 | 限制单交易复杂度 |
| Weight Budget | 权重预算 | 控制 REAP 对区块空间占用 |
| Dust | 微额输出 | 经济上不可花费的小额输出 |
| Dust Fold | Dust 折叠 | 将小额返还并入税，避免垃圾输出 |
| Tax | 税额 | REAP 从输入中扣除的比例 |
| Refund | 返还额 | 回流到原脚本/聚合输出的部分 |
| Mempool | 内存池 | 未确认交易暂存区 |
| Template | 区块模板 | 矿工组块候选 |
| Coinbase | 出块奖励交易 | 收取补贴与手续费 |
| Replay Attack | 重放攻击 | 在另一链复用签名/交易语义 |
| Replay Protection | 回放保护 | 让签名域跨链不可复用 |
| SigHash | 签名哈希类型 | 决定签名覆盖范围 |
| Domain Separation | 域隔离 | 不同协议上下文使用不同签名域 |
| Tagged Hash | 标签哈希 | 用特定 tag 区分消息域 |
| Legacy Script | 传统脚本路径 | 非 witness 的签名验证路径 |
| SegWit v0 | 隔离见证 v0 | 改进签名覆盖与可扩展性 |
| Taproot | 隔离见证 v1 | 引入 Schnorr 与更灵活脚本路径 |
| Key Spend | Taproot 密钥路径花费 | 直接用内部公钥签名花费 |
| Script Spend | Taproot 脚本路径花费 | 通过脚本叶子与控制块花费 |
| Namespace Isolation | 命名空间隔离 | 地址/端口/密钥版本防混链 |
| Bech32 HRP | 地址人类可读前缀 | 区分链与网络 |
| HD Key Version | 扩展键版本字节 | 防止 xpub/xprv 跨链误用 |
| Coin Type | BIP44 币种编号 | 钱包分层路径隔离 |
| Auto-Renew | 自动续期 | 钱包后台周期续期机制 |
| Failure Backoff | 失败退避 | 失败后延迟下一轮，防止风暴 |
| Per-Run Budget | 单轮预算 | 限制每轮续期总额 |
| MinConf | 最小确认数 | 控制候选输入安全性 |
| Fee Rate | 费率 | 影响交易被打包概率与成本 |
| Dry Run | 演练模式 | 不广播交易，只输出候选/计划 |
| Reorg | 链重组 | 主链回滚并切到更优分支 |
| Flaky Test | 不稳定测试 | 受时序/环境影响偶发失败 |
| DoS | 拒绝服务攻击 | 通过资源消耗影响可用性 |
| Determinism | 确定性 | 同输入同规则得同输出 |
| Invariant | 不变量 | 任意流程都必须成立的约束 |

## 10. 结论

OBTC 当前实现已从概念提案进入可执行协议系统阶段，其核心价值体现在三点：

1. **规则可执行**：Expiry、REAP、Replay Protection 具备明确激活与失败语义。  
2. **跨层闭环**：Consensus、Mining、Wallet 三层形成端到端一致路径。  
3. **风险可治理**：通过参数化、硬约束、退避与预算把风险收敛到可控区间。  

后续优化重点不是继续堆叠机制，而是提升现有机制的运营质量：

- 增强运行期可观测性；
- 降低大规模场景中的波动与不确定性；
- 提升对用户与外部生态的解释一致性。
